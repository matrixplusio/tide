# 产品方案

## 一句话

Tide 是运维的发布操作台：**把"谁在什么时候把哪个制品放到哪个环境"变成一条有记录、
不可抵赖的路径。**

它自己不部署任何东西 —— 部署由 Argo CD 做，改部署仓由 Kargo 做。Tide 负责的是
发起、确认、留痕，以及把整个过程呈现出来。

## 要解决的问题

现在的发布流程是 Confluence + Jira + 升级系统三件套，**三者之间没有关联**：

- Confluence 上有发布说明、SQL 脚本、Nacos 配置变更
- Jira 上有工单和审批
- 升级系统执行镜像升级

信息靠人脑对照。最典型的事故场景是"服务升上去了但 SQL 没跑"—— 没有任何系统能
提前拦住它，因为没有一个系统知道这次发布的完整定义。

Tide 要补的就是这块：**发布的执行和记录收口到一处**，并且和 Jira 工单建立硬关联。

## 边界：Tide 做什么，不做什么

| | 归属 |
|---|---|
| 审批 | **Tide**：发布策略按环境配置审批规则（指定用户或组、任一 / 全部 / 至少 N 人），确认后进入审批；Jira 仍记录工单号 |
| 发布说明、SQL 全文 | **Confluence**。Tide 链接过去，不搬运内容 |
| 执行镜像升级、重启、部署仓配置同步，看部署过程 | **Tide** |
| 部署仓配置的 diff | **Tide** 在配置同步单里展示 Argo CD 算出的差异，审批人和审计都看这一份 |
| 执行 SQL、改 Nacos | 运维在各自的工具里做，Tide 第一版不碰 |
| 指标、长期趋势 | **Grafana**。Tide 只显示"这次发布正不正常"所需的当前状态 |

**不把 SQL 全文搬进 Tide** —— 那会变成一个劣质的文档系统，而且和 Confluence 两份
内容迟早不一致。Tide 要的是"这次发布关联了哪些前置变更"，不是变更的内容本身。

## 谁用

全部是运维操作。**默认拒绝**：新账号（含 SSO 首次登录自动创建的）在被授权之前，
服务、发布单、审计都看不到。管理员在管理后台用角色 × 用户或组 × 环境范围授权，
还能再按项目和服务类型收窄，例如只让某个组发布某个项目在生产类环境的后端服务。
内置 `admin` / `operator`（发布者）/ `viewer`（只读）三个角色。

首次部署在网页上完成：用 Pod 日志里的 setup token 证明有集群权限，创建本地管理员，进系统后
再在设置里接上游和 SSO。

个人资料、密码、登录会话在「个人中心」自助管理。

## 核心流程

```
运维登录（SSO，或本地账号）
  → 看上百个服务在 dev/qa/uat/prod 的版本和健康状态
  → 选服务 + 目标环境
  → 选制品（默认只列已在上游环境跑过的）
  → 填 Jira 单号 + 原因
  → 确认倒计时（清单 + 异常高亮）
  → 命中审批规则的先等审批（任一 / 全部 / 至少 N 人）
  → Tide 调 Kargo API 创建 Promotion
  → 看执行过程：Kargo 步骤 / 滚动进度 / Pod / 日志
  → 全程写审计
```

dev 环境是全自动的（Kargo 发现新镜像就部署），但**同样在 Tide 里可见** —— 版本、
Pod、日志、自动部署历史。另外提供两个手工操作：暂停自动部署（调试时不想被覆盖）、
部署指定制品（回到旧版本复现问题）。

## 三道防线

审批、确认倒计时、审计。前两道拦住这一次，第三道让事后说得清。

### 审批

规则在「管理 → 发布策略」按环境配，可以再按项目和服务类型细分；命中多条时取最
具体的一条。规则指定谁能批（用户或组）和通过条件（任一 / 全部 / 至少 N 人）。

发起人自己不算一票。审批和驳回都写审计，发布单详情里能看到谁批的、什么时候。
没配规则的环境确认完直接执行 —— 审批是选项，不是所有环境都值得这道手续。

### 确认倒计时

**是强制阅读时间，不是强制等待时间。** 倒计时期间显示完整清单并高亮异常项；倒计时
结束后按钮才可用，且必须主动点。默认 10 秒，在「管理 → 发布策略」里可改。

不能到点自动执行 —— 人可能在这几秒里被打断，回来发现已经发了。

异常项要自己跳出来，人不该靠逐行核对去发现它们：

- 版本回退（目标版本比当前旧）
- 首次部署（该环境从没跑过这个服务）
- 跨多个版本
- 上游环境验证时间不足

真正出事的从来不是"点错了按钮"，是"清单里有一项不该在里面而没人看见"。

### 审计

**append-only，只能插入，不能改删。** 记的不是"操作成功了"，是决策链：

```
谁 · 什么时候 · 哪个服务 · 哪个环境
从 digest A → digest B
关联的 Jira 单号
执行结果 / 失败原文
```

**digest 而不是 tag** —— tag 可以被重新指向，事后追溯时只有 digest 能证明"当时跑的
到底是什么"。

**Jira 单号是必填的。** 有了它，"这次变更对应哪张工单"和"工单里说的那个版本是不是
真的部署上去了"才有答案 —— 而这恰恰是现在三套系统脱节时答不上来的问题。

## 状态机

```
draft ──提交──▶ confirming ──10s 确认──▶ executing ──▶ succeeded
                     │                        │
                     └──取消──▶ cancelled      └──▶ failed
```

**`succeeded` 的含义是新版本真正在跑，而不是请求发出去了。** 升级：Kargo 晋级成功之后，
还要等工作负载换成目标镜像、**全部副本都是新版本且就绪、旧版本 Pod 全部退出**，才算成功；
重启同理（重启后创建的 Pod 全部就绪）；配置同步是 Argo CD 同步操作成功、需要时重启完成、全部工作负载滚动就绪。新版本起不来时，Kubernetes 超过
`progressDeadlineSeconds` 判定滚动失败，发布单随即标为 `failed` 并写明原因；上游一直没有终态则按执行超时失败。
批量发布里，后一个执行顺序要等前一个顺序的条目按这个标准全部完成才开始。

**`failed` 之后不允许重试同一张单，要新建。** 失败后集群状态已经变了，旧的上下文
（当时看到的版本、当时的异常提示）不该自动适用于新的尝试。

**同一个服务 + 环境同时只允许一张单在 `confirming` 或 `executing`。** 靠数据库的
部分唯一索引，不靠应用层检查 —— 两个请求同时到达时应用层挡不住。

## 为以后留的结构：发布单

**数据模型按"一张发布单包含多个条目、条目可以是不同类型"设计**：

```
发布单 REL-2026-0917-03 → prod    Jira: OPS-1234

  [sql]    seq 1   user 表加索引             → Confluence 链接
  [config] seq 2   request-timeout 30s→60s    → Confluence 链接
  [image]  seq 3   portal-api      v2.13.2 → v2.14.0
  [image]  seq 3   task-worker              v4.0.0  → v4.0.1
```

已实现 `image`（升级）、`restart`（重启）和 `sync`（配置同步：把部署仓里镜像以外的变更经 Argo CD 同步到集群，
建单时存下差异，执行前重新比对，只改 ConfigMap / Secret 时自动重启）。`sql` 以后接入时同样是**新增一个执行器**，
发布单、审计、顺序控制、状态机全部复用，不改表不迁数据。

`sequence` 字段现在就要有 —— SQL 必须先于服务升级，这个顺序是发布的固有属性，
不是以后才需要的功能。

这样做的另一个好处：批量升级（一次发布涉及一组服务）天然就支持了，因为它只是
"一张单里有多个 image 条目"，而不是一个需要特殊处理的功能。

## 第一版不做

- **执行 SQL / 改 Nacos** —— 运维在各自工具里做，Tide 只记录关联（部署仓里的配置走「配置同步」）
- **回滚按钮** —— 回滚就是"用旧制品再发起一次升级"，走同样的流程。单独做个按钮
  容易让人以为回滚不需要确认
- **发布窗口** —— 禁止某些时段升 prod
- **制品对比** —— 两个版本之间有哪些 commit
