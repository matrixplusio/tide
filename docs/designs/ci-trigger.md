# CI 触发发布

流水线推完镜像通知 Tide 一次就结束，由 Tide 接管到发布完成。本文记录**为什么这样做**
以及边界在哪。接口字段见 `docs/api.md`。

## 出发点

原方案是 webhook 直接通知 Kargo 自动晋级。Kargo 的 `argocd-update` **只等同步结束，
不等 Pod 就绪** —— Promotion 成功 ≠ 发布成功。Tide 会继续轮询 Argo CD 的 resource
tree，要求新一代被观察到、副本全部更新且就绪、没有多余旧副本才算成功。批量发布时这个
差别会放大：Kargo 说全成了，实际可能有几个还在滚或者滚挂了。

所以让 CI 通知 Tide 而不是通知 Kargo。

## 决策

| 项 | 决策 | 理由 |
|---|---|---|
| 谁改 git | **仍然是 Kargo** | Tide 不引入 git 库。它决定「发什么」，Kargo 执行「改 tag 并 push」，Argo CD 同步，Tide 判定生命周期。三者职责不变 |
| CI 等不等 | **不等**，调一次拿到 2xx 就结束 | 审批 + 发布 + 健康检查要几分钟到十几分钟，等待会占满 runner；而且发布失败不该让「构建」变红 —— 镜像明明建出来了 |
| 通知失败 | **不让 job 红**（`\|\| echo`） | 镜像已在仓库里，可以在 Tide 里手动发起。因为一个 webhook 超时把构建判失败才是错的 |
| 幂等 | **数据库唯一索引**，键默认取 digest | CI 重跑、人工重跑都不能重复发布。放在应用层判会有并发窗口 |
| 触发方式 | **每个环境各自配**：`off` / `approve` / `auto` | dev 想自动、prod 想审批，是同一个机制的两个档位 |
| 认证 | 独立的机器令牌，不是会话 | 令牌不是人：不能浏览任何东西，只能打这一个端点 |

### 为什么要排队等制品

CI 推完镜像那一刻，Kargo 的 Warehouse 还没扫到，Freight 不存在，`plan.Build` 无从谈起。
Warehouse 的发现间隔是分钟级。

所以请求**只记录一条 intake 就返回**，后台 worker 每 20 秒看一遍等待中的 intake，
找到对应 digest 的 Freight 再建单。等满 30 分钟仍没有就标记超时。

这也是 CI 侧不用重试的原因：重试制造重复，耐心留给 Tide。

## 流程

```
CI push 镜像
  └─ POST /api/v1/ci/releases（一次，不等）
       └─ ci_intake 记一行 waiting
            └─ worker 轮询：digest 对应的 Freight 出现了吗
                 ├─ 没有 → 继续等（30 分钟后标记超时）
                 └─ 有 → 建发布单 + submit（认领目标）
                      ├─ 环境 ci=approve → 停在待确认，通知渠道
                      └─ 环境 ci=auto   → 直接执行
                           └─ 该环境配了审批规则 → 仍然走审批
```

## 自动发布放弃了什么

`Releases.Start` 跳过**阅读读秒**。读秒保护的是「一个人正要按按钮」，自动路径没有这个人，
强制读秒只会白等。

其余一条没少：

- **审批规则照样生效**。自动不等于免批。
- **封版照样拦**。封版是关于环境的，不是关于谁发布的。
- **目标认领照样做**。同服务同环境仍然只允许一个在途发布单。
- **阈值照样拦**。验证时长、跨版本、未同步配置在强制的环境里照样拒绝。
- **审计照样写**，而且**写成另一个动作**：`release.confirm.auto`，不和人工的 `release.confirm` 混。
  主体是令牌（`ci:<id>`），detail 里有 `auto: true`、流水线地址、GitLab 触发人和 commit。
  界面上发布单列表和详情页都带「⚡ 自动」标识，详情页的进度写「自动放行」而不是「已确认」——
  「已确认」会声称有人读过。

### 没有人确认，意味着什么

`approve` 档位下，发布单停在待确认，由人在 Tide 里核对制品并确认 —— **确认人不必是建单人**
（建单人是个令牌）。确认时仍要回显 digest，所以那个人必须说清自己在发什么。

`auto` 档位下没有人确认。审计里确认的主体是令牌名，**不冒充任何人**。给 prod 开 `auto`
等于这个环境没有人工闸门，开不开由部署方决定；开关是管理员专属，改动进审计。

### Jira 单号和发布说明

发布策略要求填的，流水线填不了。Tide **不替它编** —— 缺了就把 intake 标失败，
写清楚缺哪一项。生成的流水线片段会把 commit 标题作为发布说明带上，单号需要流水线自己传。

### 未同步的配置

没人在场决定「要不要把未同步的 git 变更一起发出去」，所以**一律不带**（`withConfig=false`）。
在把配置漂移设为强制的环境里，这会直接拒绝；其余环境记为异常项。

## 令牌

`tide_ci_` + 32 字节随机，库里只存 SHA-256。

不用 bcrypt：令牌本身是满熵的，没有可爆破的空间，而每次 CI 请求都付一次密钥拉伸的代价
不值得。**密码**用 bcrypt 是因为人选的密码熵低，两者的威胁模型不同。

撤销和不存在给**同一个答复**（2030），调用方只能知道「这个令牌不好使」。

令牌在建单那一刻会**再验一次**：通知和发布之间被撤销的令牌不会发布成功 —— 凭据要在**改动发生的那一刻**有效，不是只在宣告的那一刻。

## 已知限制

- Warehouse 扫到之前 intake 一直是 `waiting`。如果 Warehouse 压根没监听这个仓库，
  要等满 30 分钟才会显示超时。页面上能看到在等什么。
- intake 超时/失败只进审计和 CI 页面，**不发聊天通知**。发布本身的成功失败走原有的通知规则。
- 一次 intake 对应一个服务一个环境。批量发布仍然只有人工路径。
