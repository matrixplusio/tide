# 洞察

> 状态：已实现。接口契约以 `docs/api.md` 为准。

发布台记下了每一次发布的完整决策链。这一页把那些记录反过来读：**不是「发生了
什么」，而是「我们加在路上的那些拦截，到底有没有改变过结果」**。

## 为什么不进 Prometheus

`docs/architecture.md` 里那批 `tide_*` 指标回答的是系统问题：接口延迟、上游健康、
执行器有没有卡住。这一页回答的是**业务问题**，两者的数据形态不一样：

| | 系统指标 | 业务指标 |
|---|---|---|
| 维度 | 路由、状态码、上游主机 —— 有界 | 服务名、人名、Jira 单号 —— 无界 |
| 时间 | 最近一段，够告警就行 | 任意时间段，「上季度」是常见问题 |
| 重启 | 进程内计数器归零，可以接受 | 归零就等于失忆 |
| 运算 | 求和、分位数 | 分组、关联、排序、去重 |

把人名和服务名放进 Prometheus 的 label 会把 TSDB 撑爆；而「近一年的审批通过率」
在一个保留期几天、重启清零的时序库里根本问不出来。

所以这一页**直接查 PostgreSQL**。代价是每次都要扫一遍时间段，收益是精确、可回溯、
可以任意分组 —— 而且**不需要新增任何埋点**：`releases`、`release_items`、
`release_approvals` 里已经有全部原始记录。

少数几个适合告警的标量（异常项忽略率、审批中位耗时、CI 自动发布失败率）以后可以
再做成指标，那是另一件事。

## 三类问题

### 一、这些拦截起作用了吗

这是这一页存在的理由。Tide 的设计里埋了几条**假设**，它们都可以被证伪：

| 指标 | 在验证哪条假设 | 数字难看时说明 |
|---|---|---|
| 确认页停留时长分布 | 「倒计时是强制阅读时间」 | 绝大多数落在刚过倒计时的那一档 = 人在等它走完，不是在读 |
| 异常项高亮后照发的比例 | 「异常项会自己跳出来」 | 比例高不一定是人的问题，也可能是阈值太敏感，告警成了噪音 |
| 审批驳回率与等待时长 | 「审批是一道闸门」 | 驳回率接近 0 且中位等待几十秒 = 橡皮图章，只增加了延迟 |
| CI 自动 vs 人工的失败率 | 「自动不等于免批」 | 这是唯一能回答「自动化到底更可靠还是更危险」的数字 |
| 同一人建单并确认的比例 | 双人原则的实际覆盖 | 不是错（多数环境没有审批规则），但这些单只经过一双眼睛 |

确认停留时长只统计 `source = 'ui'` 的发布：CI 触发的自动发布跳过读秒，把它们算进
去会把分布拉向零，看上去像「所有人都没读」。

### 二、活跃度

服务、环境、变更类型、时段分布，以及人员的**工作量分布**。

**人员那块刻意不做成排行榜**：按名字排序而不是按数量降序，失败数和这个人建的总数
并排显示。指标一旦变成目标就不再是好指标 —— 一个按发布次数排名的榜会让人去拆单。
CI 令牌也会出现在这张表里，但带「令牌」标记：它们发的单是真实工作量，只是没有人
在一单一单地做决定。

时段分布用**看的人自己的时区**（浏览器 `Intl` 解析出来，作为 `tz` 参数传给服务端）。
「周六凌晨 2 点发了一次 prod」只有在本地时区下才读得出异常。

### 三、值得看一眼的

不是要优化的数字，是要有人看一眼的信号：

- **目录覆盖率** —— 服务目录里有多少服务经 Tide 发过。这个数字直接回答「Tide 是不是
  真的成了发布的入口」，比任何使用量统计都实在。
- **版本回退次数** —— 目标制品比当前在跑的旧，是发布质量最直接的代理指标。
- **同一天反复发布** —— 同服务同环境一天三次以上，通常是在救火。
- **同一单号多次发布** —— 一个 Jira 单号覆盖太多次发布，「这次变更对应哪张工单」
  就没有答案了，而那正是 Jira 单号必填的理由。

## 可见性

走 `audit.view`，和审计页同一条规则、同一套 `visibility` 过滤：**一个人只看得到
自己有权限范围内的数据**。范围限定到某些项目的人，看到的每一个数字都只统计那些
项目的发布。

**人员那一节只对能看到全部环境的人显示。** 部分范围下的工作量数字会诱发一个不成立
的比较：看到的只是这个人在你可见范围内做的事，不是他做的全部。宁可不给。

服务目录要靠上游才能读到，而发布历史不需要。所以上游没配或连不上时，**只有覆盖率
和项目名缺失，其余照常** —— 这一页不该因为 Kargo 挂了就整页打不开。

## 为什么不是 increase()

一开始 Grafana 那份仪表盘用 `increase(tide_releases_finished_total[$__range])` 数发布
次数，结果把 5 次发布显示成 16 次：`increase` 会按窗口边界线性外推，而发布是稀疏
事件，数据只占窗口的一小段时。

这里的数字全部来自 SQL 的 `count(*)`，没有这个问题。这也是「业务问题查库、系统问题
查时序库」这条分界的一个具体理由。

## 页面怎么摆

三类问题各自成节，节与节之间靠标题和留白分开，不靠边框 —— 这是
`docs/ui-design.md` 那三条里的第二条。

数字用总览页已有的 `.card`：独立卡片、12px 间距。**第一版用了 1px 的发丝线
把几个数字隔在同一张白底上，结果看着就是一整块**，浅色模式下尤其。两个页面
说一个数字的方式也应该一致，不该各造一套。

每个数字都带一句说明它是「几分之几」。一个百分比脱离了分母就会被读成比它
实际更强的结论 —— 「成功率 100%」在只有两次发布时毫无意义。

图表是纯 CSS。四种形状不值得引一个图表库，而且这些图的数字本来就以文本形式
写在旁边 —— 人真正读的是那个数字，图只负责让比例一眼可见。热力图的颜色深浅
另配 tooltip 说明具体次数，颜色不单独承载信息。

## 性能

每次报告是十几条聚合查询，都带时间范围。迁移 `0017` 加了支撑它们的索引：
`releases(created_at)`、`releases(env, created_at)`、`release_items((payload->>'service'))`、
`release_items(release_id)`、`release_approvals(release_id, decided_at DESC)`。

时间范围**强制上限一年**（`insights.MaxRange`），默认 90 天。无上限的范围等于让
调用方决定数据库做多少工作。

报告没有缓存：它是管理员偶尔打开的页面，不是每个请求都走的路径，而缓存会带来
「看到的数字是什么时候的」这个新问题。
