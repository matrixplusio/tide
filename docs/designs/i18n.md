# 国际化（i18n）

Tide 界面与 API 消息支持 `zh-CN` 和 `en`，已全部实现。本文记录**为什么这样做**，
以及改动文案时该往哪里改。日常改一条文案看 `docs/development.md`。

## 决策

| 项 | 决策 | 理由 |
|---|---|---|
| 服务端文案 | 按 `Accept-Language` 渲染，`msg` 仍是可直接显示的句子 | §4.2 的契约不变；上游错误原文透传依赖它 |
| 语言 | `zh-CN` + `en`，`zh-CN` 为默认 | |
| 审计 | **固定英文**：action 名、`detail` 内容不随界面语言变 | 审计是留证材料，同一条记录在谁的屏幕上都该读起来一样 |
| 通知 | **固定默认语言** | 发到共享频道，不属于任何人的会话，没有"读的人的语言" |
| 发布单标题、异常消息 | **固定默认语言**（存进数据库） | 同审计：存下来的文本是证据，不能因读者而变 |
| 用户录入的数据 | **原样显示** | 环境显示名、分类维度名、发布单标题（手填的）属于配置和输入，不翻译 |
| 语言来源 | `Accept-Language`，前端显式发送当前界面语言 | 见下 |

## 架构：结构化错误，边缘渲染

服务端的难点不是"把中文换成键"，而是**产生错误的地方不知道语言**：
`internal/validate` 和各领域包在深处构造错误，那里没有请求上下文。

所以错误在产生时携带 **消息键 + 参数**，只在**唯一的出口** `respond.Fail` 渲染成句子 ——
它持有 `*gin.Context`，locale 在那里是已知的。

```
领域/校验层            errcode 层                respond（唯一出口）
FieldError{           Error{                    envelope{
  Field: "id",          Code: 1007,               code: 1007,
  Key:  "p.format",     Fields: [...],            msg: i18n.T(locale, key, args),
  Args: [...],        }                           data: {fields: [{field, msg}]}
}                                               }
```

要点：

- `errcode` 的表存**键**不存句子，`Code.DefaultMsg(locale)` 渲染。**码本身不变**。
- 读错误文案一律用 `Error.Text(locale)`，**不要读 `Msg`** —— 走默认文案时 `Msg` 是空的。
- `validate.FieldKey(field, key, args...)` 报错；参数里如果也是 `i18n.Key`（例如字段标签），
  `i18n.T` 会用同一 locale 一并翻译，句子和里面的名词不会一个中文一个英文。
- 请求结构体的 `label` 标签存**键的末段**（`label:"username"`，不是 `label:"label.username"`）：
  标签会进 validator 的命名空间字符串，而 `fieldPath` 按点切分，带点的键会把
  `username` 变成 `username.username`，前端就无法把错误挂回字段。
- **例外**：上游（Kargo / Argo CD / Registry）错误原文不翻译，按 §4.2 原样透传并截断。

### locale 从哪来

`middleware.Locale()` 解析 `Accept-Language`，匹配 `zh-CN` / `en`，匹配不上取默认，
存进 `context.Context`。

前端**显式发送当前界面语言**，而不是让浏览器自己的偏好来回答：

```ts
headers: { 'Accept-Language': currentLocale(), ... }
```

否则字段标签来自前端、标签下面的错误来自后端，浏览器是 en-US 而界面是中文时两者会打架。

### 前端

`react-i18next`，两份目录打进包里。`en.ts` 用 `Messages`（`typeof zhCN`）做类型约束，
少一个键直接编译失败。

纯函数（状态名、权限名、校验规则）用模块级 `i18n.t`，不是 hook；因此
**切换语言会整页重载** —— 只有订阅了 hook 的组件会重渲染，其余会留着旧语言的文案，
半中半英比一次重载更糟。

## 五道防线

每一道都验证过：把它保护的东西弄坏，测试会失败。

| 测试 | 防什么 |
|---|---|
| `i18n.TestCatalogsAgree` | 某个语言缺键 |
| `i18n.TestVerbsMatch` | 同一键在两种语言里参数个数不同（认识 `%[2]s` 显式索引） |
| `i18n.TestEveryMessageRenders` | 格式渲染不出来，用户看到 `%!s(MISSING)` |
| `i18n.TestSharedRuleWordingMatchesTheWebClient` | 前后端共享校验规则文案不一致（CONVENTIONS.md §8） |
| `web/src/locales/keys.test.ts` | `t('typo.key')` —— 键不存在时 i18next 显示键名本身，TypeScript 看不见 |

加上 `en.ts` 的类型约束，共六层。

## 已知限制

`i18n.Default` 是编译期常量 `zh-CN`。存进数据库的文本（审计 detail、通知、发布单标题、
异常消息）都用它渲染，所以**英文团队部署时这些仍是中文**。

要支持的话：把 `Default` 改成读启动期配置（`TIDE_DEFAULT_LOCALE`），语义不变
（存下来的文本固定、所有人读到同一份），只是让部署方决定那一份是什么语言。
目前没有这个需求，没做。

## 不在范围内

- 原生 `<input type="datetime-local">` 的显示格式跟浏览器 locale 走，页面无法控制
  （Chrome 用浏览器 locale，不是 `<html lang>`）。要统一只能自绘日期控件，
  可访问性风险不小，单独评估。展示用的时间由 `fmtTime` 统一格式，不受影响。
