# 多副本、缓存与状态划分

Tide 以 `replicas: 2` 运行。本文记录**哪些状态放哪里、为什么**，以及为此修掉的两个缺陷。

## 两个副本分别在干什么

| 工作 | 谁做 | 并行 |
|---|---|---|
| HTTP 请求 | **两个副本都做**，Service 负载均衡 | 是 |
| 服务目录快照 | 谁先要谁建，其余副本读同一份（配了 Redis 时） | 是 |
| executor 推进循环 | 持 advisory lock `7419002` 的那个 | 否 |
| CI intake worker | 持 advisory lock `7419003` 的那个 | 否 |

两把锁是分开的，**两个后台循环可以落在不同副本上**。`replicas: 2` 主要买的是可用性
（`maxUnavailable: 0` 的滚动升级、节点 drain），不是后台吞吐 —— 那两个循环做的是 IO 等待。

## 修掉的两个缺陷

### 设置在另一个副本上永远不生效

`settings` 的进程内缓存**没有任何过期时间**，`Invalidate()` 只清本进程。在 A 上改的设置，
B 到进程重启为止都看不到：

- 在 A 设的**封版拦不住**走 B 的发布
- 把环境的 **CI 触发从 auto 改成 off**，B 照样接受调用并自动发布
- 改了**审批规则**、轮换了**上游 token**、停用了**通知渠道**，B 一概不知

这是安全边界失效。修法见下面的代数。

### CI intake worker 没有选主

两个副本各建一张发布单，其中一张撞上目标唯一索引被取消，那条 intake 被标成 `failed` ——
**CI 页面显示「失败」，而另一张单其实正在发布**。executor 早有选主，这个没有。

## 划分：什么放 PostgreSQL，什么放 Redis

判断只看四件事：是事实来源还是派生数据、要不要和别的写入同一个事务、要不要能查询/审计、实测有多热。

### 留 PostgreSQL —— 事实来源

发布单及其条目与审批、`release_counters`（单号靠事务内自增）、`audit_log`
（**append-only 是数据库权限保证的**，运行账号只有 INSERT/SELECT）、`settings`（含加密凭据、
改动要审计前后值）、身份与授权、`ci_tokens`、`ci_intake`。

### 留 PostgreSQL —— 实测后确认

| | 直觉说该进 Redis | 实测 / 事实 |
|---|---|---|
| `sessions` | 每请求都读 | `/me` 中位 7.0ms，`/healthz`（不碰库）6.2ms —— **数据库部分只占 0.8ms**。而且会话要能列出、撤销、写审计 |
| 登录限流 | INCR 更快 | 计数**从 `audit_log` 数**。换成独立计数器会出现「审计说没锁、计数器说锁了」的分裂：限流依据和留证必须是同一份记录 |
| `captcha_challenges` | 天然 TTL | 一次登录一条 |

### 留 PostgreSQL —— 哪怕别处也能做

**选主**：advisory lock 活在**干活的那条连接上**。「有权执行」和「能执行」于是是同一件事，
连接断了两者同时消失。租约式的锁会在一次长暂停后过期而持有者仍以为自己是 leader，
两个 leader 同时动手；要堵上得加 fencing token，而 token 只能由被保护的资源校验 ——
那个资源就是 PostgreSQL。

**缓存代数**：必须和它描述的那次写入原子提交。事务外的任何机制都有窗口：

```
先写库再通知   → 中间崩 → 库是新的，别人永远不重读
先通知再写库   → 别人在 COMMIT 前重读，读到旧值又缓存起来 → 一样永久不一致
```

### 放 Redis —— 派生数据

| | 收益 |
|---|---|
| 服务目录快照 | 副本间**逐字节一致**；上游调用 N→1；读 1–2ms，重建 45–70ms（本地 7 个服务，按上百个服务外推 0.3–1s） |
| 镜像详情 | 按 digest 不可变，天然可共享 |

## 一条硬规则

> **Redis 里不允许存在任何一份「唯一副本」的数据。**

每一条都能从 PostgreSQL 或上游重建。于是 Redis 是**软依赖**：

- Redis 挂 → 退回「每个副本自己建」，也就是加它之前的行为。不会错、不会丢
- Redis 被清空 → 下次请求重建
- Redis 被攻破 → 泄露服务名、镜像地址、digest 这类内部拓扑，**没有凭据、没有会话**
- `TIDE_REDIS_URL` 留空 → 用进程内实现，不用改代码

配了但连不上则**启动失败**，不静默降级 —— 否则运维会以为副本共享着缓存，其实各存各的。

## 代数怎么工作

`cache_generation` 一个 scope 一行（`settings` / `access` / `catalog`），在做出改动的那个
**事务里**自增。每个 HTTP 请求在中间件里取一次，整个请求内所有缓存看到同一个世界。

Redis 的 key **带上代数**：

```
tide:catalog:snapshot:<gen>
```

于是「失效」不是一条会丢的消息，而是**大家去读另一个 key**。旧 key 没人再引用，靠 TTL 回收。
镜像的 key 不带代数 —— 一个 digest 指向一份不可变的 manifest。

## 已知代价

- 代数变化时，两个副本会**各重建一次**快照（配了 Redis 则只有一个建，另一个读）。
  这是每次真实变更一次，不是每 30 秒一次。
- `policyTTL`（5 秒）保留，但现在只是空闲副本重读计数器的下限，不再是改动生效的延迟。
