# 信息架构

上百个服务、若干个环境、多种角色。结构一开始想窄了会在服务数量上来之后彻底塌掉，
所以先把导航和分类定死。

## 导航

| 入口 | 回答什么问题 |
|---|---|
| **总览** | 现在有什么在执行、有什么等我审批、上游连得上吗 |
| **服务** | 某个服务在各个环境分别是什么状态 |
| **发布单** | 正在执行和历史的发布，每一单的完整过程 |
| **审计** | 谁在什么时候做了什么，按 Jira 单号、服务、人检索 |
| **洞察** | 这段时间发布了多少、拦截起没起作用、哪里值得看一眼 |
| **管理** | 访问控制、发布配置、系统配置（按权限显示） |
| **我** | 个人资料、密码、登录会话 |

**审计单独做入口**，不藏在管理里。审计是两道防线之一，而且查审计的场景很具体
（"OPS-1234 这张单最后部署了什么"、"昨晚谁动了 prod"），需要一个能直接检索的地方。

**洞察和审计分开**，因为问的是两种问题：审计回答「这一件事是谁做的」，洞察回答
「这一类事发生了多少次、我们加的拦截有没有改变过结果」。两者读同一批记录，走同一
套权限范围，详见 `docs/designs/insights.md`。

**导航按权限显示**。没有 `audit.view` 的人看不到审计入口，没有任何管理权限的人
看不到管理入口 —— 不是进去之后才被拒。

## 服务怎么分类

平铺列表在上百个服务时不可用。三个维度，**主维度是业务域**：

**主分组：业务域**

业务域不是 Tide 内置的分类，而是从 Argo CD Application 的 label 读出来的
（管理 → 服务目录里配置读哪个 label）。没配 label 时，取部署目标 namespace
去掉「-环境名」后缀，例如 `acme-dev` → `acme`。

选它做主维度的理由：**它和权限、配额、NetworkPolicy 的边界一致**。人脑子里
"这个服务属于哪一块"的答案本来就是它，不是"它是 A 级还是 B 级"。

**筛选维度一：服务类型**

同样来自 label。Tide 不内置任何一套类型名 —— 每个组织的分法都不一样，写死
就一定有人对不上。管理 → 服务目录里指定读哪个 label、取值怎么排序和显示。

运维视角下这个维度最有用：同类服务的故障模式相同。它也是授权的维度之一
（"这个组只能发某一类服务"）。

**筛选维度二：自定义维度**

除了业务域和类型，还能再配若干个 label 作为筛选器，例如服务级别。用在
"出事了先看核心服务"这种场景。不做成主维度是因为它在日常操作里用得少。

**搜索**优先于分类。真正知道自己要找什么的人会直接搜 —— 搜索框在服务页顶部
常驻，支持服务名模糊匹配。

## 集群与服务状态

Tide 不做监控（那是 Grafana 的事）。它只回答**和发布相关的状态**：

**集群级**（总览页顶部、侧边栏常驻）
- 每个上游的 Kargo / Argo CD / Registry 连得上吗 —— 连不上时相关操作提前禁用
  并说明原因，而不是让人点了之后报错
- 各环境的服务数，以及有多少个处于"非预期状态"

**服务级**（服务列表 + 详情）
- 各环境当前制品（tag + digest）
- Argo CD 的同步状态（Synced / OutOfSync）和健康状态（Healthy / Degraded / Progressing）
- 有没有在途的发布单

**部署过程必须在 Tide 里看完，不能跳去 Argo CD 和 Kargo。** 升到一半要开另外
两个系统才知道进展，等于这条流程没有真正收口。所以发布单详情要有：

- Kargo 的晋级步骤（拉仓库 → 改镜像引用 → 提交 → 推送 → 等同步）各自状态
- 滚动更新进度（几个副本切到新版本了）
- Argo CD 管的资源各自的 Synced / Progressing
- Pod 列表，以及**每个 Pod 的日志和事件**

升级完看日志和工作负载状态是发布流程的一部分，不是额外功能 ——"升完了吗"
这个问题的真正答案是"新副本起来了、日志里没报错"，而不是"Promotion 显示成功"。

**但指标不做：CPU / 内存 / QPS / 延迟留在 Grafana。** 那是长期趋势，和"这次
发布成没成"是两件事。在这里重复一遍只会让人以为 Tide 是监控系统，然后在它
数据不准时抱怨。服务详情放一个跳转链接就够。

## 审批与权限在界面上的位置

**审批是 Tide 的一部分**，规则按环境配置（管理 → 发布策略），可以再按项目和
服务类型细分；命中规则的发布单在确认之后进入审批，等指定的人或组批准
（任一 / 全部 / 至少 N 人）才开始执行。Jira 单号仍然必填，它记录的是工单，
不是审批本身。

**待审批是导航上的常驻信息**：侧边栏显示"N 个等待你审批"，点进去就是筛好的
发布单列表。审批人不该靠别人在群里喊。

**授权模型是角色 × 主体 × 环境范围**（管理 → 角色与授权）。角色定义"能做什么"
（权限点的集合），主体是用户或组，环境范围限定"在哪些环境"，还能再按项目和
服务类型收窄。**默认不授予任何角色** —— 新账号在被授权之前看不到任何东西，
放开是改授权，不是改代码。

**可见性也按授权走**：服务、发布单、审计记录只列出人有权限的那部分，新账号
默认什么也看不到。

**界面上的体现**：没有权限的操作入口直接禁用并说明原因，不是填完表单点了
提交才被拒。

**列表只读，操作只在环境详情页里。** 服务列表把各环境并排做横向对比，但列表上
没有任何操作入口 —— 要操作必须先点进某个环境。这样目标环境永远是明确选定的，
而不是"从哪进来就是哪个"那种隐含的上下文。误操作的真正来源是后者。

## 制品列表怎么扛住规模

一个服务跑久了会有几百个制品（按每天 2-3 次构建算，一年就是 999 个）。
平铺列出来既慢又没法选。

**默认只显示"能升到目标环境的"**，这是最有效的一刀：

- 升 uat 时，默认只列**已在 qa 跑过**的制品 —— 没在 qa 验证过的本来就不该上 uat
- 升 qa 时，默认只列**已在 dev 跑过**的

这一条就把几百个降到个位数，而且它不是"为了性能而隐藏"，是**流程本身的要求**。

在这之上：

| 手段 | 说明 |
|---|---|
| 分段筛选 | `可升级 / 全部` —— 想看全部时一键切换 |
| 搜索 | 按语义版本、commit、构建标签匹配 |
| 分页 | 默认 20 条，滚动加载 |
| 时间范围 | 最近 7 天 / 30 天 / 全部 |

**版本号两层显示。** 构建标签 `20260916151427-46b7619f-0022` 是机器标识，人记不住
也没法口头沟通。所以主标识用语义版本：

```
v2.14.0   20260916151427-46b7619f-0022
主         次要（灰色、等宽）
```

`v2.14.0` 从 Git tag 来，CI 构建时写进镜像 label
（`org.opencontainers.image.version`），Tide 读出来展示。人说"升到 v2.14.0"，
机器锚定的仍然是 digest。

**如果没有打 Git tag 的习惯，这一层就是空的**，界面上只能显示构建标签。要不要
引入语义版本，是个需要业务侧配合的决定。

## 页面清单

```
总览
├── 上游连通性（每个上游的 Kargo / Argo CD / Registry）
├── 待我处理（等我审批 N、我发起的在途 N）
└── 最近活动

服务
├── 搜索 + 业务域分组 + 类型与自定义维度筛选
├── 服务列表（各环境版本横向排开，只读）
├── 服务详情
│   ├── 各环境当前版本 + 副本就绪数 + 健康状态
│   ├── 该服务的发布历史
│   └── 跳转 Grafana（只有指标跳出去）
└── 环境详情（每个环境一个）
    ├── 当前版本、副本、健康
    ├── Pod 列表 → Pod 详情（日志、事件、探针、当前资源）
    ├── 该环境的部署历史
    ├── 自动部署的环境：暂停自动部署 / 部署指定制品
    └── 发起升级 / 重启 / 配置同步 → 填 Jira 单号 → 确认倒计时

发布单
├── 分段：执行中 / 等我审批 / 失败 / 全部
├── 批量发布（一次选一组服务，粘贴服务名与版本）
└── 发布单详情
    ├── Jira 单号、发起人、原因、来源（人工 / CI 自动）
    ├── 条目列表（每个服务的 from → to、各自状态）
    ├── 审批记录（谁批的、什么时候）
    ├── Kargo 晋级步骤
    ├── 滚动更新进度 + Argo CD 资源状态
    ├── Pod 列表 → Pod 详情
    └── 失败时：错误原文 + 服务是否受影响 + Git 是否已变更

审计
└── 按 Jira 单号 / 服务 / 环境 / 操作人 / 时间检索

洞察
├── 这段时间发生了什么（发布数、成功率、没发出去的）
├── 这些拦截起作用了吗（确认停留、异常忽略率、审批、人工 vs CI）
├── 活跃度（服务 / 环境 / 类型 / 时段 / 工作量分布）
└── 值得看一眼的（目录覆盖率、回退、同日重复、单号复用）

管理（按权限显示）
├── 访问控制：用户 · 组 · 角色与授权
├── 发布：环境 · 上游 · 服务目录 · 发布策略 · 通知 · CI 触发
└── 系统：登录与安全 · SSO · 通用

我
└── 个人资料 · 密码 · 登录会话 · 我的授权 · 我的活动
```

## 取舍的顺序

时间不够时按这个顺序砍：

1. **先砍**：自定义维度筛选、Grafana 跳转、暂停自动部署、通知推送
2. **再砍**：环境详情里的部署历史（发布单页能看到全部）、Pod 的事件和资源
3. **不能砍**：服务按业务域分组、搜索、确认倒计时、Jira 单号、审计、执行过程可见

不能砍的都是"没有它就失去存在意义"的：没有审计和 Jira 单号，Tide 就只是换了个
皮的旧升级系统；没有执行过程可见，运维还是得开 Argo CD 和 Kargo。
