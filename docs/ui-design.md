# 界面设计

Apple 风格。但"Apple 风格"不等于圆角加毛玻璃 —— 那是表象。真正要抄的是三条：

1. **信息密度低，但信息量不低。** 留白不是浪费，是让重要的东西自己浮出来。
2. **层次靠材质和位置，不靠边框和色块。** 一屏里如果每个模块都有边框和背景色，
   那等于没有层次。
3. **颜色是功能性的。** 强调色只有一个，语义色只在表达状态时出现。用颜色区分
   "不同的东西"是设计偷懒。

## 色彩

```
强调色     #007AFF   系统蓝。整个界面只有这一个强调色
成功       #34C759   部署成功、审批通过
警告       #FF9500   待审批、执行中
危险       #FF3B30   失败、驳回
```

中性色不用纯灰，用带一点蓝的冷灰 —— 和系统蓝同一个色温，界面才像一个整体：

```
浅色                     深色
背景    #F5F5F7          #000000
面板    #FFFFFF          #1C1C1E
分隔线  #D2D2D7          #38383A
主文本  #1D1D1F          #F5F5F7
次文本  #6E6E73          #98989D
```

两套都要做。不是为了炫技 —— 运维半夜看发布状态的场景真实存在。

## 字体

```css
font-family: -apple-system, BlinkMacSystemFont, "SF Pro Text",
             "Helvetica Neue", "PingFang SC", sans-serif;
```

Apple 设备上直接用到 SF Pro，其他平台优雅退化。中文用苹方（`PingFang SC`），
它和 SF Pro 的字重、字面都是配套设计的。

**digest 和 tag 必须用等宽字体**（`ui-monospace, SF Mono, Menlo`），并且加
`font-variant-numeric: tabular-nums`。这两样东西是要被人逐字符核对的，比例字体
下 `0` 和 `O`、`1` 和 `l` 会看错 —— 而在这个系统里看错一个字符意味着批准了错误的
制品。

## 三个关键界面

### 1. 服务总览

一行一个服务，横向展示各环境当前版本。这是运维最常看的一屏，回答"现在什么状态"。

```
                 qa              uat             prod
portal-api       0916-46b7  ●    0915-a3f2  ●    0915-a3f2  ●
task-worker      0916-8821  ◐    0914-bb10  ●    0914-bb10  ●
media-api        0916-c0de  ●    0916-c0de  ●    0915-7d31  ●
```

设计要点：

- **同一个制品在多个环境时，视觉上要能一眼看出**。相邻环境版本相同时用淡色连接线
  串起来 —— 这比让人逐个核对 tag 快一个数量级。
- **状态点用形状 + 颜色双编码**，不只用颜色（色觉障碍者约占男性 8%）：
  `●` 正常、`◐` 执行中、`■` 非预期（OutOfSync 或非 Healthy，但未失败）、`▲` 失败、`○` 未部署。
- 正常状态的标签用中性色，只有异常才上语义色——每行一个绿点已经表达了"正常"，再叠一个绿色标签就是色块。
- 相邻环境同制品的连线用淡灰色：它表达"相同"，不是一种状态，不能占用成功色。
- 版本号只显示 `MMDD-<commit前4位>`，完整 tag 和 digest 在悬停或详情里。

### 2. 发起升级

选制品这一步是整个系统最需要谨慎的地方，界面要帮人做对：

```
┌──────────────────────────────────────────────────┐
│  portal-api  →  uat                              │
├──────────────────────────────────────────────────┤
│  ○  20260916151427-46b7619f-0022                 │
│     sha256:a942939aef8d…    16:14  已在 qa 运行   │
│                                                   │
│  ○  20260916094312-8821ac0e-0021                 │
│     sha256:3f1c88b02e14…    09:43                │
└──────────────────────────────────────────────────┘
```

- **"已在 qa 运行"这个标记是关键信息**，不是装饰。它直接回答"这个制品验证过吗"。
- digest 始终可见，不折叠。折叠起来的信息等于不存在。
- 时间用相对时间（"2 小时前"）还是绝对时间？**绝对时间**。发布是需要和别的事件
  对时间线的，"2 小时前"在事后回看时毫无意义。

### 3. 发布单详情

状态时间线是主体。每个节点记录时间和人：

```
   ●  已提交          16:20   张三
   │  "修复登录超时问题"
   ●  已批准          16:25   李四
   │
   ◐  执行中          16:25
   │  Kargo Promotion: uat.01m2n8.46b7619f
   ○  完成
```

失败时不要只显示"失败"。把 Kargo 的错误原文放出来 —— 运维要的是能直接搜的
错误信息，不是被包装过的友好提示。

## 动效

只在两个地方用：

- **状态变化**：执行中的脉冲、成功时的短促缩放。让人知道"这里刚刚变了"。
- **页面转场**：160ms 的位移 + 淡入。超过 200ms 就开始显得慢。

不要做加载骨架屏的波浪动画、不要做按钮的涟漪扩散。Apple 的动效克制是因为
**动效的目的是解释空间关系，不是表演**。

`prefers-reduced-motion` 要尊重，全部降级成瞬时切换。

## 一条硬规则

**"批准"按钮不能是界面上最显眼的东西。**

它是不可逆操作的入口。在 Apple 的人机指南里，破坏性和不可逆操作从不做成主按钮的
视觉重量 —— 因为界面的视觉引导会真实地影响人的手速。

批准前要让人确认看到了 digest：确认弹窗里重复展示一次 tag 和 digest，而不是只问
"确定吗"。
